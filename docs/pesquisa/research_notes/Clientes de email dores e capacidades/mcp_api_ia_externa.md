# MCP / APIs for external AI agents in email and calendar clients (state of the art, October 2026)

Research date: 2026-10-11. **MCP spec in force: revision `2026-07-28`** (the previous revision, `2025-11-25`, is still what most SDKs implement, including the official Swift SDK).

## Q1. Which email/calendar products ship MCP servers today, and what tools do they expose?

### Takeaway
By late 2026 the big mail providers ship first-party remote MCP servers using Streamable HTTP and OAuth: Google Workspace (Developer Preview), Microsoft 365 Work IQ (preview, needs a Copilot licence), Fastmail (GA, April 2026) and Superhuman Mail (beta, Business plan). They follow one pattern: read, search and draft tools are generous, while **sending is either missing (Google) or gated behind a separate permission or confirmation (Fastmail, Superhuman)**. On macOS, Apple Mail has no official server. Community servers drive Mail.app through AppleScript or read its SQLite database directly.

### Cited Findings
**Google Workspace (first party, Developer Preview)**
- Each Workspace product gets its own remote MCP server, all at `/mcp/v1`: `gmailmcp.googleapis.com`, `calendarmcp.googleapis.com`, plus Drive, Docs, Sheets, Slides, Chat and People. They use Streamable HTTP and OAuth 2.0, and the status is "Developer Preview Program" — [Google: Configure the Workspace MCP servers](https://developers.google.com/workspace/guides/configure-mcp-servers)
- Gmail tools: `create_draft, get_message, get_thread, label_message, label_thread, list_drafts, list_labels, search_threads, unlabel_message, unlabel_thread`. **There is no send tool.** Drafts are meant to be reviewed and sent from Gmail. Scopes: `gmail.readonly`, `gmail.compose` — [Google docs](https://developers.google.com/workspace/guides/configure-mcp-servers)
- Calendar tools: `create_event, delete_event, get_event, list_calendars, list_events, respond_to_event, search_events, suggest_time, update_event` — [Google docs](https://developers.google.com/workspace/guides/configure-mcp-servers)
- Google announced the agent tools at Cloud Next '26 and opened the Workspace MCP server as a public developer preview in May 2026 — [Workspace Updates blog, May 2026](https://workspaceupdates.googleblog.com/2026/05/agent-tools-and-security-updates-for-workspace-developers.html)
- A third-party review notes that the `gmail.compose` scope technically allows sending, so the credential can send even though no tool does — [vorplabs review](https://vorplabs.com/agent-tools/gmail-mcp) (secondary source)
- The installed Claude plugin in this environment shows a slightly larger live Gmail tool set (it adds `trash_*`, `mark_*_spam`, `apply_sensitive_*_label`, `update_message_labels`, `get_draft`). This suggests the tool surface is still growing during the preview. (Observed in this session's tool list, not in a public document.)

**Microsoft 365 (Work IQ / Agent 365, preview)**
- The Agent 365 catalog lists a **Work IQ Mail** server (create, update and delete messages, reply and reply-all, semantic search) and a **Work IQ Calendar** server (create, list, update and delete events, accept and decline, resolve conflicts), plus Copilot, SharePoint, OneDrive and Teams — [Microsoft Learn: Work IQ MCP overview](https://learn.microsoft.com/microsoft-agent-365/tooling-servers-overview)
- Admins allow or block these servers in the M365 admin center, and a block applies to every user and agent — [Microsoft Learn](https://learn.microsoft.com/microsoft-agent-365/tooling-servers-overview)
- A Microsoft dev blog (June 2026) describes Work IQ as "production-ready", collapsing "hundreds of operations into just 10 generic tools" — [Microsoft 365 Dev Blog](https://devblogs.microsoft.com/microsoft365dev/work-iq-production-ready-intelligence-for-every-agent/). This conflicts with the per-server catalog framing above, and the packaging is unresolved.
- Requires a Microsoft 365 Copilot licence and Entra app registration. The MCP tools cover less than Graph does (no inbox rules or folders, for example) — [Scalekit comparison](https://www.scalekit.com/blog/outlook-mcp-vs-api) (third party)

**Fastmail (first party, GA)**
- Endpoint `https://api.fastmail.com/mcp`, authenticated with OAuth 2.0 (API token as an alternative). Users pick access levels: **read-only** (search and read mail, contacts, calendars), **write** (drafting, moving, deleting, editing contacts and calendars) and **send**. More than one level can be selected — [Fastmail Help](https://www.fastmail.help/hc/en-us/articles/15869557281295-Connecting-AI-tools-via-Fastmail-s-MCP-server)
- Launched on National Email Day, April 22, 2026. Fastmail stresses it has no built-in AI: the MCP server is "simply another API endpoint" — [Releasebot summary of Fastmail release notes](https://releasebot.io/updates/fastmail) (aggregator)

**Superhuman Mail (beta)**
- Hosted MCP at `https://mcp.mail.superhuman.com/mcp`, added in Claude Code with `claude mcp add --transport http ...` and OAuth sign-in. It searches across Gmail and Outlook accounts, summarizes, drafts, sends and manages the calendar. **"Every send requires your approval"** by default. Requires a Business plan or higher — [Superhuman Help](https://help.superhuman.com/hc/en-us/articles/49810745762067-Superhuman-Mail-MCP-Server-Beta); [Superhuman feature page](https://superhuman.com/mail/features/email-mcp)

**Zapier MCP (aggregator)**
- Gmail actions include Add Label, Archive, Delete, Create Draft, Create Draft Reply, Create Label, **Send Email** and Remove Label. The user chooses which actions to expose. Zapier advertises 9,000+ apps and 30,000–40,000+ actions (its own pages give different figures) — [Zapier Gmail MCP](https://zapier.com/mcp/gmail); [Zapier docs](https://docs.zapier.com/mcp/get-started/your-first-mcp-workflow)

**Apple Mail (community only)**
- `sweetrb/apple-mail-mcp` (Node) reads, sends, searches and manages mail via AppleScript — [GitHub](https://github.com/sweetrb/apple-mail-mcp)
- Other community servers: `maximbilan/apple-mail-mcp-go` (Go, ships an `.mcpb` one-click Claude Desktop bundle), `s-morgan-jeffries/apple-mail-fast-mcp` (23 tools: 9 read-only, 14 mutating), `BastianZim/apple-mail-mcp` (reads Mail's database directly and needs Full Disk Access), and `jayvee6/apple-mail-mcp` (osascript plus an optional MailKit bridge) — [ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fmaximbilan%2Fapple-mail-mcp-go); [LobeHub](https://lobehub.com/mcp/s-morgan-jeffries-apple-mail-fast-mcp) (via search summaries)
- Community Fastmail servers (for example `pyfastmail-mcp`, about 42 tools over JMAP, CardDAV, CalDAV and WebDAV) warn that they "can send email, delete messages, and modify contacts/calendars" — [mcpservers.org](https://mcpservers.org/ko/servers/pjosols/pyfastmail-mcp)
- Community Google Workspace servers such as taylorwilsdon's (Gmail, Calendar, Docs and more, over stdio) predate Google's own — [Glama listing](https://glama.ai/mcp/servers/aaronsb/google-workspace-mcp)

### Inferences
- The common tool set is: search threads, get thread or message, list labels or folders, label and unlabel or move, archive or trash, create draft or reply draft, list, search, create and update events, respond to an invite, suggest times or check free/busy. A native client should match this vocabulary so agents that already "know" Gmail or Outlook tools carry over.
- The industry default is **"draft, never send", or send as a separate, explicitly granted permission that needs confirmation**. A new client should do the same.
- A native client has a differentiator that cloud MCPs lack: one server spanning **all** of the user's accounts (Gmail, Outlook, iCloud, IMAP) with local search and an offline index. Superhuman's cross-account search is the closest analogue.

### Gaps
- I found no Shortwave MCP server or public API in the searches, and its status is unknown.
- I could not verify the exact Microsoft Work IQ tool names, or whether it is one gateway or separate servers.
- Calendar write scopes for Google's MCP are not listed in its docs, which show read-only scopes only.
- I did not look into Spark/Readdle, Proton, Hey or Spike.

## Q2. What are the major security risks and recommended mitigations?

### Takeaway
An email MCP server is the textbook **"lethal trifecta"**: it holds private data, takes in untrusted content (every inbound email is attacker-controlled input) and can communicate externally (send, forward, reply, calendar invites, even fetching remote images or links). Prompt injection has no reliable fix, so security has to be **architectural**: remove or gate the exfiltration leg (no autonomous send), use least-privilege scopes and per-tool permission tiers, require human confirmation on the app side for send, forward or delete, keep an audit log, and offer read-only modes. Supply-chain attacks on MCP servers that handle email have already happened in the wild.

### Cited Findings
- The lethal trifecta is private data access, exposure to untrusted content, and the ability to communicate externally. When all three meet in one agent, an attacker can instruct the model to fetch private data and send it out. Guardrails that stop "95% of attacks" are a failing grade in security, and the only safe approach is to avoid the combination — [Simon Willison, "The lethal trifecta", June 16, 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Willison notes that MCP "encourages users to mix and match tools from different sources", so the legs of the trifecta can come from different servers. His canonical example is the GitHub MCP exploit: malicious public issues led to private repo data leaking through a PR — [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Calendar and email injection, demonstrated:** "Invitation Is All You Need" (Nassi, Cohen, Yair/SafeBreach, Black Hat 2025) hid prompts in calendar invite titles and email subjects. When the user asked Gemini to summarize their week, the hidden prompts triggered actions, including smart-home control set off by phrases like "thank you". The paper covers 14 scenarios across 5 attack classes. Google added filtering and user confirmations, but "there's no reliable fix in sight" — [Bitdefender](https://www.bitdefender.com/en-us/blog/hotforsecurity/gemini-ai-compromised-through-malicious-calendar-invites-researchers-warn); [The Decoder](https://the-decoder.com/attackers-can-hijack-google-gemini-with-a-simple-prompt-hidden-in-a-calendar-invite/)
- **First malicious MCP server in the wild:** the npm package `postmark-mcp` v1.0.16 (Sept 17, 2025), a look-alike of a legitimate project, added one line that **BCC'd every email sent to the attacker** (phan@giftshop[.]club). It had about 1,500 weekly downloads, and the publisher deleted it when contacted — [The Register](https://www.theregister.com/2025/09/29/postmark_mcp_server_code_hijacked/); [Dark Reading](https://www.darkreading.com/application-security/malicious-mcp-server-exfiltrates-secrets-bcc); [CSO Online](https://www.csoonline.com/article/4064009/trust-on-mcp-takes-first-in-the-wild-hit-via-squatted-postmark-connector.html)
- MCP spec (2026-07-28) on tools: "there **SHOULD** always be a human in the loop with the ability to deny tool invocations". Clients should show which tools are exposed, flag invocations, and confirm sensitive operations. Servers **MUST** validate inputs, implement access controls, rate-limit and sanitize outputs. Clients **SHOULD** show tool inputs before calling ("to avoid malicious or accidental data exfiltration") and log tool usage for audit — [MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- The spec says "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers", and hosts "must obtain explicit user consent before invoking any tool" — [MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [MCP spec overview](https://modelcontextprotocol.io/specification/latest)
- **Confused deputy and token passthrough:** MCP servers **MUST** validate that tokens were issued for them (audience, RFC 8707), "**MUST NOT** accept or transit any other tokens", and implementations must follow the security considerations on mix-up and confused-deputy attacks — [MCP spec: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Scope minimization: `scopes_supported` should be the minimal set, with more scopes requested through step-up authorization (`403 insufficient_scope`) — [MCP spec: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Product precedents for mitigation: Google removes send entirely ([Google docs](https://developers.google.com/workspace/guides/configure-mcp-servers)); Fastmail splits read, write and send into separate grants ([Fastmail Help](https://www.fastmail.help/hc/en-us/articles/15869557281295-Connecting-AI-tools-via-Fastmail-s-MCP-server)); Superhuman requires approval for every send ([Superhuman Help](https://help.superhuman.com/hc/en-us/articles/49810745762067-Superhuman-Mail-MCP-Server-Beta)); Microsoft gives admins allow and block controls ([Microsoft Learn](https://learn.microsoft.com/microsoft-agent-365/tooling-servers-overview))

### Inferences (recommended design for a native client)
- **Confirmation must live in the mail app, not only in the MCP host.** Client-side confirmation (Claude Desktop "Allow?") can be auto-approved, and annotations are only hints. For `send`, `forward`, `delete permanently`, `create rule/filter`, `set auto-reply` or adding external attendees, the server should either (a) only create a draft and return "queued for review in the app", or (b) block until the user approves in a native app sheet showing the exact recipients and body. MCP's multi-round-trip `input_required` elicitation (Q5) can carry this, but the native UI is the stronger control.
- **Permission tiers per connected client:** Off / Read-only / Read + organize (label, archive, snooze) / Draft / Send (each send confirmed). Settings should also be scoped per account, so a user can expose a personal account but not a work one, plus per-mailbox exclusions.
- **Break the exfiltration leg:** never auto-load remote images or follow links when rendering content for tools; return plain text with links neutralized or annotated; strip hidden HTML and CSS text (white-on-white, `display:none`) that is a common injection vector; flag "external sender" and "first-time sender" in structured output so the agent and user can weigh trust; cap how much data a single call returns.
- **Watch for recipient anomalies:** on a send or forward, warn when a recipient never appeared in the thread or address book, or a BCC appears, or the body contains large blocks quoted from other threads. This is a direct counter to the postmark-mcp pattern.
- **Audit log** in the app: every tool call with client identity, arguments, result size and approval decision, and a one-click "revoke this client".
- **Supply chain:** shipping a first-party, code-signed server inside the app bundle (rather than asking users to `npx` a third-party package) is itself a security selling point.

### Gaps
- I found no published, quantified data on prompt-injection success rates against email-specific MCP servers.
- I did not fetch the MCP "Security Best Practices" page or the authorization security-considerations subpage in full. They hold more detail on confused deputy and session hijacking.

## Q3. What is the best architecture for a local MCP server bundled with a sandboxed macOS app?

### Takeaway
The pattern that works with the most clients is a **small, signed CLI helper embedded in the app bundle** (for example `MyMail.app/Contents/MacOS/mymail-mcp` or `Contents/Helpers/`). MCP hosts launch it over **stdio**, and it is a thin protocol shim that forwards requests to the running main app, which owns the accounts, tokens and index, over an authenticated IPC channel (an XPC Mach service through an App Group, or a Unix socket in the App Group container). An optional **localhost Streamable HTTP** endpoint, with a bearer token or OAuth, serves clients that prefer URLs. Remote or cloud MCP is a separate product decision because it needs server-side mail access. A Mac App Store build is feasible but needs care: the helper inherits sandbox restrictions, and IPC has to go through App Group containers or XPC.

### Cited Findings
- The official Swift SDK `modelcontextprotocol/swift-sdk` targets macOS 13+ (also iOS 16 and visionOS) and needs Swift 6 / Xcode 16. It is pre-1.0 (installed with `from: "0.11.0"`) and implements spec **2025-11-25**, not yet 2026-07-28. Transports: `StdioTransport`, `HTTPClientTransport`, `StatelessHTTPServerTransport`, `StatefulHTTPServerTransport` (sessions and SSE), `InMemoryTransport` and `NetworkTransport` (Network.framework TCP/UDP). Server features: tools, resources (with subscriptions), prompts, completions, sampling, elicitation (form and URL), progress, bearer-token validation and Protected Resource Metadata for OAuth, and graceful shutdown via swift-service-lifecycle — [GitHub swift-sdk README](https://github.com/modelcontextprotocol/swift-sdk)
- A GUI app needs a deliberate bridge to its MCP server, such as a bundled helper or an XPC service. A helper the app launches directly through `Process` or fork/exec **inherits the app's sandbox** and creates no new privilege boundary. launchd manages an XPC service, starting it on demand and restarting it after a crash, and Apple notes that "in many cases, an XPC service is a better choice". Mac App Store distribution requires App Sandbox. App Groups provide shared containers and IPC (XPC, Unix domain sockets), and these channels should be treated as internal APIs that validate and authorize every request. Keep stdout for protocol messages only and log to stderr — [macmyths: How to build an MCP server for a Mac app](https://macmyths.com/how-to-build-an-mcp-server-for-a-mac-app/) (secondary guide summarizing Apple and SDK docs)
- **EasyMacMCP** is described as built for sandboxed, App Store-compatible Mac apps. It uses **named pipes** between the sandboxed app and a helper executable because stdio access can be restricted in the sandbox — (search summary of [mcp-template / EasyMacMCP](https://tomevault.io/tome/adamwulf/mcp-template); not verified first-hand)
- **Real-world precedent:** Macuse ships a Claude Desktop `.mcpb` bundle and, for other clients (Cursor, Codex, Raycast, VS Code, Warp, Zed, LM Studio, Windsurf), points the config at the binary inside the app: `/Applications/Macuse.app/Contents/MacOS/macuse mcp` — [macuse-mcp](https://gitblind.noratr.app/macuse-app/macuse-mcp)
- Claude Desktop config on macOS lives at `~/Library/Application Support/Claude/claude_desktop_config.json`, and hosts launch stdio servers as child processes — (as listed in several server READMEs; see the [macmyths guide](https://macmyths.com/how-to-build-an-mcp-server-for-a-mac-app/))
- Spec transports: **stdio** (local subprocess) and **Streamable HTTP**. HTTP+SSE is formally Deprecated. As of 2026-07-28, Streamable HTTP has **no protocol sessions** (`Mcp-Session-Id` removed), no `initialize` handshake, a required `server/discover`, and `subscriptions/listen` for change notifications. Servers keep cross-call state through explicit handles passed as tool arguments — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Auth: stdio implementations "**SHOULD NOT** follow [the OAuth] specification, and instead retrieve credentials from the environment". HTTP servers follow OAuth 2.1 with PKCE, RFC 9728 Protected Resource Metadata (**MUST**), RFC 8707 resource indicators (**MUST**) and RFC 9207 `iss` validation. **Client ID Metadata Documents** are preferred, and Dynamic Client Registration is now deprecated — [MCP spec: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

### Inferences (recommended architecture)
1. **A capability core in the main app** (Swift package `MailCapabilities`) owns accounts, OAuth tokens (in the Keychain), the local index and the send pipeline. It exposes typed operations (`searchThreads`, `getThread`, `createDraft`, `requestSend`...) with an explicit `caller` parameter that drives policy, tier checks and audit.
2. **An `mcp` helper CLI embedded in the bundle**, signed and sandboxed with the App Group entitlement. It runs `StdioTransport` from the Swift SDK and forwards each tool call over **XPC (a Mach service registered by the main app or a login item)** or a Unix socket in the App Group container. Mail credentials never live in the helper, so it holds no secrets. If the main app is not running, the helper can launch it (or a background login-item agent via `SMAppService`) or return a tool error saying "open MyMail".
3. **Client identification and pairing:** the first time a new client connects (stdio `clientInfo`, or the parent process's code signature checked through the audit token), the app shows a native "Allow Claude Desktop to read your mail? [Read only / Organize / Draft]" prompt. That grant is stored per client.
4. **Optional local HTTP endpoint** (`127.0.0.1` only, random port, per-client bearer token, or OAuth with CIMD for spec correctness), for clients configured by URL. This needs the `com.apple.security.network.server` entitlement in the sandbox. Enforce Origin and Host checks against DNS rebinding.
5. **Distribution:** offer one-click install (generate a `.mcpb` bundle for Claude Desktop, and copy-paste config snippets or deeplinks for Cursor, Claude Code and Raycast). Under the Mac App Store sandbox the app cannot write other apps' config files, so the user has to paste them or grant access through an open panel. A Developer ID (direct) build has more freedom here.
6. **Remote MCP (later):** only relevant if the product has a backend. Otherwise the local-first design is a privacy feature: data never leaves the Mac except to the LLM the user chose.

### Gaps
- I found no authoritative Apple or Anthropic document confirming that a Claude Desktop-spawned helper from an App Store-sandboxed bundle works without issues. The inherited-sandbox behaviour when a third-party process (not the app) launches a sandboxed helper needs testing. Such a helper is not "launched by the app", so its own entitlements apply, and its App Group access depends on signing.
- App Review stance on bundled CLI helpers that external apps execute: no source found.
- The Swift SDK's timeline for 2026-07-28 support is unknown. In the interim the server will speak 2025-11-25, which current clients still accept.

## Q4. How do App Intents / Apple Intelligence integrate, and can one capability layer serve both MCP and App Intents?

### Takeaway
App Intents (with App Entities and App Schemas for the mail domain) is Apple's surface for Siri, Shortcuts, Spotlight and Apple Intelligence. MCP is the surface for third-party LLM hosts. As of October 2026 **Apple Intelligence does not call MCP tools and external agents cannot invoke App Intents directly**. The reports of Apple adding MCP to App Intents are based on beta code (September 2025) and unconfirmed claims about iOS/macOS 27. The best practice is **one Swift domain layer with two thin adapters** (AppIntent wrappers and MCP tool handlers), with authorization enforced in the domain layer using an explicit caller identity.

### Cited Findings
- App Intents run on-device under the app's entitlements and are available to Siri, Shortcuts and Spotlight from installation. MCP tools are discovered by hosts at session start over stdio or Streamable HTTP. "Apple Intelligence doesn't call MCP tools", and external agents can't invoke App Intents. The two differ in identity (`AppEntity` gives system-tracked IDs), rendering (the system versus the host model) and discovery. **Recommendation: one Swift domain layer, thin adapters, with the domain enforcing authorization through an explicit caller argument.** iOS 27 adds `LongRunningIntent` and `SyncableEntity` (beta) — [Blake Crosley, "App Intents vs MCP"](https://blakecrosley.com/blog/app-intents-vs-mcp-tools-frontier) (third-party analysis)
- WWDC26 App Intents sessions: 343 "Explore advanced App Intents features for Siri and Apple Intelligence" (Siri responses, visual responses, interaction donations, **confirmations**); 240 "Build intelligent Siri experiences with App Schemas" (App Entities, schemas, cross-app workflows); 345 "Discover new capabilities in the App Intents framework" (ValueRepresentation, RelevantEntities, LongRunningIntent, union parameters) — [Apple WWDC26 343](https://developer.apple.com/videos/play/wwdc2026/343/); [Apple WWDC26 240](https://developer.apple.com/videos/play/wwdc2026/240/); [session 345 digest](https://github.com/ivan-magda/wwdc26-notes/blob/main/sessions/345-capabilities-app-intents-framework/digest.md)
- Developer betas of iOS 26.1, iPadOS 26.1 and macOS Tahoe 26.1 contained code suggesting **MCP support built on App Intents**. It was not user-facing — [AppleInsider, Sept 2025](https://appleinsider.com/articles/25/09/22/ios-26-could-get-a-major-ai-boost-with-the-model-context-protocol); [Computerworld](https://www.computerworld.com/article/4061614/apple-to-deploy-mcp-support-for-powerful-ai-experiences.html)
- One blog claims WWDC 2026 confirmed system-wide MCP (an MCP client in the iOS 27 SDK) — [ChatForest](https://chatforest.com/builders-log/apple-ios-27-mcp-system-wide-siri-core-ai-builder-guide/). **This is unverified:** I found no Apple primary source or WWDC26 MCP session, and the same blog makes other unverified claims.

### Inferences
- Build the capability layer once (Swift actors and services with typed inputs and outputs and a `Caller` enum: `.ui`, `.appIntent`, `.mcp(clientID)`), and add:
  - **App Intents adapter:** `AppEntity` types for `MailThread`, `MailMessage`, `Mailbox`, `Contact`, `CalendarEvent`, plus intents such as Search Mail, Summarize Thread, Archive, Snooze, Create Draft, Create Event and Open Thread. Adopt Apple's mail-domain **App Schemas** where available so Siri and Apple Intelligence understand them. Use `requestConfirmation` for sends.
  - **MCP adapter:** tool JSON schemas and `structuredContent` generated from the same `Codable` types. Entity IDs are opaque, stable handles in both adapters.
- If Apple does ship MCP bridging of App Intents in macOS 27 or later, a clean App Intents surface could expose the same capabilities to MCP hosts for free. Either way, a shared domain layer hedges that bet.
- The shared layer is also where cross-surface policy belongs: tiers, the "send needs native confirmation" rule, the audit log and rate limits.

### Gaps
- Apple's official position on MCP in macOS 27 is unconfirmed. Check developer.apple.com release notes and the WWDC26 catalog directly.
- I could not confirm the exact Apple mail-domain App Schema intents available in macOS 26/27.

## Q5. What does the current MCP spec mean for tool, resource and prompt design in an email server?

### Takeaway
Spec **2026-07-28** makes MCP stateless (no initialize handshake or sessions; explicit handles instead), turns server-initiated requests (elicitation, sampling) into **multi-round-trip `input_required` results**, moves Tasks into an extension, deprecates Roots, Sampling and Logging, and adds caching hints. An email server should use task-shaped, moderately coarse tools with structured output, opaque stable IDs, pagination, a clear split between read and write, and drafts as the default write path. Resources and prompts are optional extras.

### Cited Findings
- Major 2026-07-28 changes: protocol sessions and `Mcp-Session-Id` removed; `initialize` removed, with version and capabilities sent per request in `_meta`; `server/discover` required; `subscriptions/listen` replaces GET/SSE and `resources/subscribe`; Tasks moved to the extension `io.modelcontextprotocol/tasks`; **MRTR**: servers return `resultType: "input_required"` with `inputRequests` (for example `elicitation/create`) and the client retries with `inputResponses`; SSE resumability removed; `ttlMs`/`cacheScope` required on list results; tools returned in deterministic order; Roots, Sampling and Logging deprecated; DCR deprecated in favour of CIMD — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- The previous revision, 2025-11-25 (released Nov 25, 2025), added experimental Tasks, OIDC discovery, incremental scope consent, CIMD, icons and URL-mode elicitation — [x-cmd summary](https://x-cmd.com/blog/251128) (secondary)
- Extensions now include **MCP Apps** (interactive UI rendered inline in conversations), Tasks, and Skills over MCP — [MCP spec overview](https://modelcontextprotocol.io/specification/latest)
- Tool guidance: an optional `outputSchema` with `structuredContent` (plus serialized JSON text for backward compatibility); tool execution errors (`isError: true`) should be actionable so the model can self-correct; for stateful tools, return handles with stated lifetimes and validate authorization on every call; `tools/list` may vary by the scopes granted to the caller (so a read-only client simply never sees send tools) — [MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences (suggested tool surface for the native client)
- **Read (safe):** `list_accounts`, `list_mailboxes`, `search_messages(query, account?, mailbox?, from?, date range, has_attachment, unread, limit, cursor)`, `get_thread(id, format=text|summary)`, `get_message(id)`, `get_attachment_text(id)` (extracted text only, size-capped), `list_events(range)`, `search_events`, `get_free_busy` / `suggest_times`, `search_contacts`.
- **Organize (reversible):** `archive`, `move`, `label/unlabel`, `mark_read`, `flag`, `snooze`, `trash` (undoable), all batchable by ID list.
- **Compose (draft only):** `create_draft`, `create_reply_draft(thread_id, reply_all?)`, `update_draft`. The result includes a deep link (`mymail://draft/<id>`) that opens the draft in the app for review.
- **High-risk (off by default, each needing native confirmation):** `send_draft`, `forward`, `create_event_with_external_attendees`, `respond_to_event`, `create_rule`, `set_auto_reply`, `delete_permanently`.
- Advertise only the tools the client's tier allows (allowed by spec). Also set `readOnlyHint` and `destructiveHint` annotations as hints for hosts, but never rely on them.
- **Resources:** `mail://thread/{id}` and `mail://message/{id}` returned as `resource_link` from search, so hosts can attach them. **Prompts:** "Triage my inbox", "Draft reply in my style", "Summarize today's agenda", "Prepare for meeting X".
